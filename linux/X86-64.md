# Linux on x86-64: what differs

The Mac game is an x86-64 program, so on an x86-64 Linux machine the port changes character: the game's code can run
as it is. This page says what that takes and what stays as [FINDINGS.md](FINDINGS.md) has it for arm64, whose
headings it follows where they differ. Read from the tree at 1.20.0 on 2026-11-26; the steps are in
[PLAN.md](PLAN.md#x86-64). Nothing here has run on Linux; a statement from general knowledge says "to check".

## In short

- **The code needs no translating there.** The image is x86-64 with macOS's calling convention, which is Linux's
  too (System V AMD64). Its 5.26 million instructions make no system call, touch no segment register and use no AVX:
  the game reaches the system only through its 681 imports. The project already runs the original code in a process
  of its own this way, under Rosetta, for its differential tests (`shims/game/harness/rsimage.c`).
- **So the recompiler, the thunks and most of the runtime drop out**: no 15-minute build, the original's speed, and
  an import bound straight to a function. What the recompiler gives beside translation does not come for free:
  overrides, hook points, mid points and edits are made while translating, and need a second form as patches.
- **Or the game is translated there as everywhere else.** The generated C passes a compile check for x86-64 Linux as
  it is (the runtime's headers have a per-lane form beside the NEON one). That keeps one mechanism for every host
  and costs the build and an unknown share of speed.
- **Everything around the game is the arm64 port's**: the same imports to answer, the same shell, renderer's OpenGL
  path, audio layer and install. Three of them get easier: the OpenGL drivers of desktop GPUs have the
  compatibility profile, Steam is a native program, and no emulator stands between Steam and the game's files.
- **It is the better place to start**, the arm64 port included: it proves the pieces both share with code known to
  be right, before translation is put in front of them.
- **The Windows game already plays there** through Proton. A native build's case is its sound path (straight to
  PipeWire, with the project's input handling), its fixes and its mods, not that nothing else works.

## The machine

An x86-64 desktop with a current distribution and a discrete GPU; the first in mind runs Arch Linux with an
NVIDIA card (to check on the machine, each of these):

- **4 KB pages**, as the image's segments are aligned: they can be mapped from the file as they are.
- **OpenGL**: NVIDIA's driver and Mesa's (AMD, Intel) give a compatibility context with the ARB assembly programs.
  The arm64 port's first risk is not one here.
- **Steam**, native: its console's `download_depot` fetches the Mac depot as the installer has it fetch Learn &
  Play's on the Mac, and `steamcmd` can be told the platform.
- **PipeWire or JACK**, as on arm64.

## The same CPU and the same calling convention

| | macOS x86-64, the game's | Linux x86-64 |
|---|---|---|
| Calling convention, stack alignment, red zone | System V AMD64 | the same |
| Variadic arguments and `va_list` | registers, then the stack | the same: `printf` and its family are called as they are |
| `char`, `long double`, `wchar_t` | signed, 80 bits, signed 32 | the same |
| Callbacks | a function pointer | the same: `qsort`'s comparator, a thread's start, an audio callback are called directly |
| Thread-local storage | `gs` | `fs`; the game's code names neither |
| Symbols | `_name` | `name` |
| Where the image wants to be | 0x100000000, above a 4 GB zero page | free in a Linux process (to check) |

None of what makes [the arm64 runtime's work](FINDINGS.md#runtime) applies: no `va_list` to rebuild, no narrow
results to widen, no struct returns to move, no trampolines, no memory-order fences.

What does differ is the C library, exactly as on arm64: Darwin's layouts and numbers at the imports
([the Mac game's imports](FINDINGS.md#the-mac-games-imports)). glibc's own sizes are a little different on this
CPU (to check): a mutex is 40 bytes and thread attributes 56 (Darwin's are 64 each), and `jmp_buf` is 200 against
Darwin's 148, of which glibc's `_setjmp` writes the first 68. `setjmp` with the signal mask would write past the
game's buffer, so the game's `setjmp` is bound to the form without it.

## Two ways to run the game

| | Run the original code | Translate, as on arm64 |
|---|---|---|
| The game's code | mapped and executed | C from `gen_image.py`, compiled |
| Checked | the image's code is plain user-mode x86-64 (below); the harness runs it so under Rosetta, all 3,487 initializers | all 243 parts pass `clang --target=x86_64-unknown-linux-gnu -fsyntax-only` |
| Build | none of the game: decrypt and start | the translation, 15 minutes and more |
| Speed | the original's | to measure: no fences are needed, but the SSE helpers are per-lane C |
| Imports | bound to the function itself | thunks, as now; prototypes from the Darwin layer's header |
| Runtime | a loader and a patcher behind the same `rc_*` interface | the runtime as it is, with x86-64 forms of two assembly files and the trampoline pool |
| Overrides, hook points | a jump at the function's entry | as now |
| Mid points (136) and edits (620) | patches planned at build time: the hard part | as now |
| The overrides that are native rewrites of the same code (zlib, libpng, libjpeg, Lua, crypto, `efd`, DSP: 707 functions) | not applied: the original runs | as now |
| C++ exceptions inside the game | can work: the image has its DWARF unwind tables (2.7 MB of `__eh_frame`), which the system's unwinder reads | a throw ends the process, as on the Mac |
| A mod | the same source and `rc_mod.h`, built for x86-64 | the same |
| Kinship with the other hosts | a second mechanism to keep in step | one mechanism everywhere |

Proposed: **run the original code**, with the `rc_*` interface kept so the overrides, the built-in fixes and mods
stay one source, and decide about patches against translation when [the fixes are due](PLAN.md#x86-64). Either way
the Darwin layer is the same C functions.

### Running the original code

**The image.** A position-independent executable of four segments, all aligned to 4 KB: a 4 GB zero page, `__TEXT`
(25 MB, with 20.9 MB of code), `__DATA`, `__LINKEDIT`. No thread-local sections. Its code, disassembled and
counted: no `gs:` or `fs:` operand, no `syscall` or `sysenter`, no AVX instruction, no `rdtsc`, three `cpuid`.

**The loader** is the harness's, 377 lines, moved to Linux: `mmap` in the place of `mach_vm_allocate`, the image at
its own address with no slide (Rosetta sits there on the Mac, which is why the harness moves it), the rebases, the
binds, the 3,487 static initializers, and a trap page that names an import nobody answers. The bind is a lookup in
the Darwin layer's table by name ([the shape of the layer](FINDINGS.md#the-shape-of-the-layer)): a `same` row's
address is glibc's own function.

**What the thunks did besides the calling convention** moves or goes:

| In `gen_thunks.py` | Running the original code |
|---|---|
| Callback parameters wrapped in trampolines; the Steam callbacks' shadow vtables; Bink's I/O callbacks | gone: a game function is callable |
| The `printf` family through `rc_va` | gone: the host's `printf` |
| `pthread_create`'s 64 MB stacks, the app's 256 MB main stack | gone: the original's frames are the original's size |
| The file imports to `rc_file_*` | stays, in the table |
| The audio hooks (device properties, I/O procs, the graph) | the audio layer's own functions |
| The FFT setup kept by the built-in fix | the fix's function in the table |
| `objc_msgSend_stret`, the unwind guard, `setjmp` across guest frames | gone |

**The `rc_*` interface without a translator.** The seam, the override modules, the built-in fixes and every mod are
written against it (`rc.h`, `rc_call.h`, `rc_hook.h`, `rc_mid.h`, `rc_abi.h`, `rc_mod.h`), with the guest's
registers in an `rc_ctx`. Run directly, the registers are the CPU's:

- **Calling the game** (`rc_call_guest`, `OV_GUEST`, the seam's `GameBootstrap` and `GameFrame`): a call.
- **An override** (`F_<addr>(rc_ctx *)`) and **a hook point** (21): a jump written at the function's entry to a stub
  that saves the registers into an `rc_ctx`, runs the native code, and returns or goes on into the function's moved
  first instructions. The overrides that change behaviour are few: `online` (9 functions), `audio` (3), `mods`
  (11), and the three in the place of the engine's Objective-C.
- **An edit** (`edits.map`) is a patch of the Mac image's bytes by its nature, with a check of the old ones. Of the
  620, 459 change bytes in place and apply as they are; 161 put instructions in the place of a range, 150 of them
  longer than it, and need the range moved out of line.
- **A mid point** (136 with an address) is a call before one instruction: a jump there, with the instructions it
  covers moved out of line.

Moving instructions is the risk: a jump of 5 bytes over a shorter instruction takes the next ones with it, and
none of them may be a branch target or lose its `rip`-relative operand. Every site and byte is known when the app
is built, and the translator's front end already knows each function's instructions and branch targets, so the
plan of patches is made then, by the tools that check the tables today, and a site that cannot take a jump gets a
breakpoint instead. All 620 edits and 123 of the mid points are rearmed-mods' (its Seven-String Guitar and Plain
Packages); the built-in fixes need the hook points, their overrides and 13 mid points.

### Translating there too

The generated C and the runtime's headers are not arm64's alone: `rc_sse.h` has per-lane reference forms beside the
NEON ones, the fences fall back to compiler barriers (x86 keeps the order itself), and the rounding-mode code is
guarded. Left to write: x86-64 forms of `rc_tramp_arm64.S`, `rc_native_arm64.S` and the trampoline pool's
decoding, about 200 lines, and SSE intrinsics in the place of the per-lane forms where the speed asks for it.
Everything else is the arm64 port's [step 1](PLAN.md#1-the-tree-builds-on-linux-and-the-games-initializers-run).

## What stays the arm64 port's

- **The imports and their table** ([darwin-imports.tsv](darwin-imports.tsv)): the same image, the same 681, the
  same classes. `runtime` rows (`setjmp`, the trampolines) and what a row says of `va_list` are the translator's.
- **The shell, the audio layer, the install**, and the three native functions in the place of the engine's
  Objective-C.
- **GNU libstdc++ from the system**: the x86-64 library exports the same old ABI, for the CPU the game was built
  for.
- **Bink** through FFmpeg, and **Cg** through the shim. NVIDIA's own Cg runtime exists for x86-64 Linux; it would
  serve as a reference for the shim there, as the x86-64 Mac one does in `cg_reference`, not as a dependency.
- **Mods** as `.so` files, one build per CPU from the same source.

## Renderer

The OpenGL path through EGL, as [planned for arm64](FINDINGS.md#renderer), with a context that reports Apple's
legacy identity. Desktop drivers have what it needs (to check on the machine), so the picture is the smaller risk
here.

**Vulkan** is no more and no less an option than on arm64, where Asahi has it too: the CPU does not decide it. The
game speaks OpenGL 2.1, and there are three ways from that to Vulkan:

- **Zink**, Mesa's OpenGL on Vulkan: no code of ours, and the way out on a machine whose OpenGL driver lacks the
  compatibility profile.
- **A Vulkan backend in `libRSOpenGL`**, beside Metal's: the Metal core written again, 10,000 lines or more, with a
  SPIR-V stage for the shader translator. It would bring the picture's extras (upscaling, MSAA on the game's
  targets, control of presentation), which on OpenGL are each written again too.
- **DXVK** for Learn & Play's Direct3D 9 alone.

OpenGL first on both CPUs, and no Vulkan backend planned: on x86-64 the reason for one is weaker still, since the
drivers that make it interesting on other systems are solid here.

## Steam and the game's files

Steam for Linux is an x86-64 program, so on this host it runs beside the game with nothing between: the console's
`download_depot 221680 221682`, the DLC depots, `loginusers.vdf` and the ownership tickets under
`~/.local/share/Steam`. Valve's own library can be asked who owns the first Rocksmith's DLC, as on the Mac. The
game never talks to it: the offline Steam layer is the same.

## Learn & Play

Its 32-bit code cannot run inside a 64-bit process as it is, so the first route does not exist for it: it would be
translated as on the Mac, with the 32-bit runtime and its 4 GB window, on top of the shell, the OpenGL window and
the audio layer. Proton runs the Windows game on this host today, which leaves little reason. Not planned.

## What plays there already

The Windows game runs on x86-64 Linux through Steam's Proton, with community guides for the cable and for low
latency through WineASIO or PipeWire. A native build of the Mac game is another way to the same game, with the
project's own audio path, fixes, offline rule and mods interface, and the Mac game's songs and saves.

## How this was found

- **The translated C**: the 243 parts of a 1.20.0 build through `clang --target=x86_64-unknown-linux-gnu
  -fsyntax-only` with the build's defines and a five-line `string.h`; no diagnostics.
- **The image**: its load commands read from the file (segments, alignment, the unwind and exception sections, no
  thread-local ones), and its code disassembled with `objdump` and counted by mnemonic and operand. The counts of
  `int`, `in`, `out` and `hlt` it also shows are data inside the code section read as instructions.
- **The harness**: `shims/game/harness/rsimage.h` and `rsimage.c`, which say what they run and how.
- **The tables**: `edits.map` and `mids.map` of `tools/targets/mac-x64` counted by form; the override lists read
  for what each module is for.
- **Not done**: nothing was built or run for x86-64 Linux, and no such machine was at hand. The driver, Steam and
  glibc statements are from general knowledge.
